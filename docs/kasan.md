# Asterinas KASAN 接入技术路线

## 目标与当前状态

本文指导后续为 Asterinas 接入内核内存错误检测器，并与 SyzAster 联合使用。
本文是设计路线，不代表仓库已实现 KASAN；文中的构建开关、模块名和报告格式
除明确标注为现有实现外，均为建议接口。

当前 SyzAster 通过系统调用驱动内核，只对 `aster_core`（旧版为
`aster_kernel`）采集 KCOV，`ostd` 不参与覆盖率插桩。系统调用仍然能够触发
`ostd` 的缺陷，但只有缺陷表现为可识别的 panic、崩溃或超时等现象时，才有
机会被发现。静默越界和释放后使用（UAF）缺少专门的检测机制。

相关现有实现见 [KCOV 架构](kcov.md)、[内核构建说明](asterinas.md)、
[编译器包装器](../src/pkg/kcov.rs) 和
[Asterinas panic 解析补丁](../patch/syzkaller/0003-pkg-report-parse-Asterinas-uncaught-kernel-panics.patch)。

首个目标平台为 `x86_64-unknown-none`，优先选择仓库已支持的 Asterinas
`v0.19.0`，其他版本在该版本完成验收后分别移植。首期检测目标为内核堆对象
越界和 UAF，随后扩展到页分配、虚拟映射、栈和全局对象。

## 工具选择与能力边界

采用软件 Generic KASAN 路线：编译器在内存访问处插入检查，运行时根据
shadow memory 判断访问区域是否可用，分配器维护对象的有效范围和生命周期。
Linux KASAN 可作为设计参考，但其配置项、内存布局、运行时和分配器钩子
不能直接当作 Asterinas 的现成功能。参见
[Linux KASAN 文档](https://www.kernel.org/doc/html/latest/dev-tools/kasan.html)。

Rust 当前官方文档列出 KernelAddressSanitizer 对 `x86_64-unknown-none`
的支持，并要求自行实现底层运行时。此结论只说明存在编译器接入路径，不能
证明目标版本固定的 nightly 已具备相同能力。必须先完成工具链探针，核对
实际参数、LLVM ABI 和代码生成结果。参见
[Rust sanitizer 文档](https://doc.rust-lang.org/unstable-book/compiler-flags/sanitizer.html#kerneladdresssanitizer)。

KASAN 不应被描述为通用 unsafe Rust 正确性验证器。其主要目标是地址访问
错误；不能据此保证不存在未初始化读取、数据竞争、Rust 引用别名违规、DMA
破坏或页表权限逻辑错误。汇编、未插桩访问和尚未适配的映射也是检测盲区。
可提取的组件可辅以宿主机 ASan 测试和
[Miri](https://github.com/rust-lang/miri)，但这些不能替代整机检测。

## KCOV 与 KASAN 的独立边界

| 区域 | KCOV | KASAN 规划 |
| --- | --- | --- |
| `aster_core` / `aster_kernel` | 保持现有插桩 | 首期可关闭，后续扩大检查范围 |
| `ostd` 常规内存访问代码 | 保持关闭 | 首期重点插桩 |
| KASAN runtime、shadow 操作和最小报告路径 | 关闭 | 禁止自插桩，防止递归 |
| 早期启动、上下文切换、特殊地址访问 | 关闭 | 逐项审计、豁免或专门适配 |
| 编译器宿主工具及过程宏 | 关闭 | 不使用内核 KASAN 插桩 |

选择范围应以实际 crate 图和最终机器码为准。泛型实例化、内联和依赖 crate
可能改变访问检查所在位置，只按源文件中是否出现 `unsafe` 选择代码并不可靠。
仅插桩 `ostd` 也可能漏掉通过其错误安全抽象在上层发生的非法访问；扩大到
safe 层和相关依赖是后续覆盖完整性工作。

始终保持 `CARGO_PROFILE_DEV_LTO=false` 和
`CARGO_PROFILE_RELEASE_LTO=false`，不通过跨 crate LTO 扩大插桩范围。
现有 `check-kcov-inst` 必须继续证明 `ostd` 没有 KCOV 回调；该检查不证明
KASAN 有效，需要另外建立验证。

KCOV 的 task-context 限制和 `try_lock()` 是覆盖率记录策略，不能照搬为
“中断上下文跳过 KASAN”。中断中的非法访问同样需要检查；首期若暂不支持
某类上下文，必须明确豁免范围与盲区，并制定后续解除条件。

## 工具链与编译器探针

在目标 Asterinas 的固定 nightly 上构建最小 `#![no_std]` 探针，记录
`rustc -vV`、LLVM 版本、目标三元组、构建 profile 和完整编译参数。

- 查询该 rustc 接受的 sanitizer 参数与目标支持情况。不要把用户态
  `-Zsanitizer=address` 直接套到裸机内核，也不要用“能编译”代替检查。
- 探针包含可观测的读写、变长访问、边界跨越访问和内存复制，避免编译器
  将待测访问优化删除。分别检查 LLVM IR、反汇编与未定义符号。
- 优先评估 outline 检查，降低初期内联 shadow 检查对启动布局的耦合。
  具体 LLVM 参数只在固定版本验证后写入构建脚本。
- 从探针提取实际 ABI 清单，包括读写检查、报告入口、变长访问及内存操作
  所需符号；例如 `__asan_load*` / `__asan_store*` 仅为可能的形式，不能
  将示例当作完整、跨版本稳定的接口。
- 核对栈、全局对象、`core` / `alloc`、原子操作和内存 intrinsic 的实际
  插桩行为。需要重建目标标准库时，将其范围和豁免规则一并固定。
- 如果现有 nightly 不支持所需能力，单独评估升级与内核兼容性，或者采用
  经验证的 LLVM pass 路径。不可在没有记录的情况下悄悄更换工具链。

交付物为可重复运行的探针、ABI 清单和支持矩阵。缺少关键回调必须导致
链接失败，禁止用空实现满足链接后宣称检测器可用。

## Shadow memory 与启动时序

Generic KASAN 常用一个 shadow byte 描述八个应用字节。可采用以下设计模型，
但 offset、地址范围和 poison 编码必须与实际编译器协议一致：

```text
shadow(addr) = (addr >> 3) + SHADOW_OFFSET
```

shadow 需要表示整段可访问、尾部部分可访问及不同不可访问状态。检查器必须
处理跨多个 shadow granule 的访问、非对齐访问、变长范围、长度为零，以及
地址加长度溢出；只检查起始地址会漏报。

实施前审计内核地址空间：内核映像、物理内存直接映射、堆、各类内核栈、
动态虚拟映射、MMIO、用户地址和 shadow 自身。给出地址区间、页表建立者、
shadow backing 来源及冲突检查。不要直接复制 Linux 的 shadow offset。

- 在任何已插桩访问发生前，准备对应 shadow 映射及有效初值。早期启动代码
  保持最小范围豁免，建立明确的初始化前后边界。
- 首期优先为实际受检区域预留 backing，避免检查过程中缺页、分配内存或
  重新进入页表管理。按需扩展要在后续验证递归和锁依赖后引入。
- 临时共享 shadow 页若用于启动，必须限制为只读或受控使用；切换到独立
  backing 后才能更新对象状态，避免不同区域互相污染。
- 估算的是受检地址对应的 shadow，而非机械地按全部虚拟地址分配物理内存。
  记录 backing、redzone、隔离队列和元数据各自的额外内存开销。
- 同一物理页的不同虚拟别名对应不同 shadow 地址。必须规定维护哪些别名，
  并测试经直接映射或其他别名访问是否绕过 poison 状态。
- MMIO 和合法用户访问要专门审计。不能为了消除误报将整个用户地址范围
  无条件视为合法，进而掩盖错误的内核指针访问。

启动验收要求：单核与 SMP 均能稳定启动；不出现 shadow 缺页、自递归或
shadow 地址与内核现有映射冲突；已声明保护的区域确实可触发检查。

## 分配器与映射生命周期

堆检测必须接入实际全局分配器及其底层对象分配路径，不能只在 syscall
入口检查参数。

- 分配时区分请求大小与实际槽位大小，只对调用者合法范围 unpoison。
  对齐填充与对象两侧 redzone 保持 poisoned，包含非八字节倍数的尾部。
- 释放前记录必要元数据，释放后 poison 用户区域。元数据放在独立区域或
  明确审计的分配器内部路径，避免空闲链表写入触发自身误报。
- realloc、清零分配、零大小分配、分配失败、布局对齐和对象复用都要定义
  shadow 状态转换；缩容后尾部应立即失效。
- 建立有上限的 quarantine 延迟复用，以提高 UAF 命中率。对象复用并重新
  unpoison 后，普通地址型 KASAN 通常不能区分旧指针与新对象。
- double-free 和 invalid-free 需要分配器元数据校验，不能声称仅靠访问
  插桩即可可靠发现。
- 页分配与释放维护对应范围，动态虚拟映射在访问前准备 shadow，在解除
  映射和地址复用时同步生命周期。页粒度保护不能替代子对象 redzone。
- 测试共享页、用户映射页、物理别名和 DMA 缓冲区；设备 DMA 写入不会自动
  经过 CPU 的编译器检查，必须保留这一能力边界。

后续单独处理栈和全局对象：核对编译器生成的元数据、注册机制及生命周期，
处理任务栈、启动栈、中断栈、上下文切换和栈回收。不能在堆检测通过后直接
宣称已覆盖 stack/global 越界或 use-after-return。

## 运行时、并发与报告

建议将 shadow 操作、访问检查、对象状态和报告组成独立内核模块；具体路径
在目标版本源码审计后确定。运行时自身及其依赖的最小调用链禁止 KASAN
自插桩，也不得引入 KCOV 回调。豁免须说明原因、调用依赖和对应验证。

访问检查路径不分配内存、不睡眠，不获取可能由被检查代码持有的普通锁。
对多 CPU 的 poison/unpoison 发布顺序给出协议，避免引入额外竞争；KASAN
本身不负责判断调用方的数据竞争是否合法。

报告路径采用预分配缓冲和最小可靠输出，支持中断及持锁上下文，防止日志、
回溯或符号解析再次进入受检分配器。设置独立的重入保护，区分检查重入与
报告重入，不能用全局跳过检查掩盖另一 CPU 的错误。

首期建议发现错误后输出首份报告并终止当前 VM，交给管理器恢复。不要在
已发生内存破坏后继续长时间 fuzz，也不要依赖用户态命令结束才能刷出报告。

建议报告至少包含：

- 固定的 KASAN 标识、错误类型、读写方向、访问宽度和故障地址。
- 故障 PC、调用栈、CPU 和任务标识；上下文不可用时明确标记缺失。
- 可获得时包含对象范围、分配与释放栈、shadow 状态及邻近 shadow bytes。
- 内核版本、构建标识、工具链和启用的检测范围，便于匹配未剥离 ELF。

错误分类只能依据已知元数据，无法确定时报告非法访问，不猜测为 UAF。

## 构建与 SyzAster 集成

建议引入独立的 `KASAN=1` 构建开关，默认关闭，不与现有 `KCOV=1` 隐式
绑定。该开关目前不是仓库的可用命令。至少保留以下构建矩阵：

| KCOV | KASAN | 用途 |
| --- | --- | --- |
| 关闭 | 关闭 | 原始基线 |
| 开启 | 关闭 | 当前覆盖率引导基线 |
| 关闭 | 开启 | 独立验证内存检测器 |
| 开启 | 开启 | 覆盖率引导与内存检测联合运行 |

编译器包装器显式区分两类插桩，保留目标和 crate 过滤，检查 runtime 豁免。
在符号检查之外检查 IR 或机器码：inline 检查未必引用外部回调，单纯 `nm`
不足以证明某段代码有无插桩。

内核产物和记录统一放到 `.workdir` 下，保存与实际启动镜像一致的未剥离
ELF、源码版本和编译参数。切换模式时隔离构建缓存，防止混用旧对象或镜像。
保留配置模板的 `__XXX__` 占位符，由用户配置 manager；脚本不自动生成或
覆盖 manager 配置。

为 `pkg/report` 增加实际 Asterinas KASAN 输出的解析与测试，验证完整报告、
截断输出、串口转义、多 CPU 交错、首次错误和嵌套 panic。已有 Linux KASAN
解析器不等于已兼容 Asterinas 的报告格式。

去重标题优先使用错误类别和稳定故障位置，避免动态地址造成报告爆炸。
验证符号化、程序最小化、独立复现及 VM 重启；复现必须使用相同检测模式和
兼容的 quarantine 配置。

## 分阶段交付与验收

| 阶段 | 交付内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| 工具链验证 | 固定版本探针、ABI 与代码生成记录 | 目标确实产生检查，豁免确实生效 |
| 最小运行时 | shadow 布局、初始化和错误输出 | 人工 poison 的非法访问可报告，合法访问通过 |
| 堆与生命周期 | 分配器钩子、redzone、quarantine | 堆越界和未复用对象 UAF 稳定检测 |
| 整机接入 | 构建矩阵、报告解析、符号化与复现 | 四种模式可启动，端到端捕获注入错误 |
| 扩大范围 | 页与虚拟映射、栈、全局对象及依赖 | 每类内存和上下文各自通过正负例 |
| 持续运行 | 长时间 fuzz 和开销评估 | 无未解释误报，记录吞吐、内存与稳定性 |

故障注入仅在专用测试镜像启用，默认构建不可通过普通接口触发。每个用例
单独启动或恢复 VM，验证报告类型、读写宽度、位置和终止行为，不能只检查
“内核崩溃了”。注入访问必须保留到机器码，避免被优化删除。

关键正负例包括：

- 合法边界访问与超出边界一字节；不同对象大小、对齐和部分 granule 尾部。
- 跨 granule 读写、变长内存操作和范围溢出检查。
- UAF、quarantine 到期、对象复用，以及 double-free/invalid-free。
- realloc 扩容和缩容、清零分配、分配失败及零大小布局。
- 多 CPU 分配释放、持锁报告、中断上下文和报告路径二次故障。
- 直接映射与虚拟别名、映射解除与地址复用；合法 MMIO 和用户拷贝负例。
- 启用相应保护后的栈和全局越界，以及任务栈切换与回收。

联合模式验收必须通过 syscall 驱动到受检代码并产生可解析的 KASAN 报告，
由 syzkaller 保存、符号化和复现；仅启动时执行自测不足以证明 fuzz 链路有效。
同时回归现有 `/dev/kcov` ABI 和 safe 层覆盖率，确保 `ostd` 仍无 KCOV 插桩。

性能比较在相同 VM 资源、syscall profile、种子、运行时长和恢复策略下进行，
记录 exec/s、内存峰值、启动时间、超时率及有效独立报告数。KASAN 增加的
开销需要用于调整超时，不能把检测器变慢误计为新内核挂死。

## 补丁组织与完成标准

Asterinas 修改以数字前缀补丁保存在 `patch/asterinas/<version>/`，不添加
`series` 文件。syzkaller 适配保存在 `patch/syzkaller/`，不直接提交子模块
工作区内的修改。编译探针、运行时、分配器钩子、报告器和宿主自动化按逻辑
拆分，每个提交保持可构建，未完成的运行时能力不能默认开启。

宿主自动化保持 Shell；如需新增 ELF 或插桩验证逻辑，放入现有 Rust 工具
体系并保持零外部 crate 依赖。不要为简单命令创建额外包装二进制。

每次实现变更应运行 `make`、`make test` 和 `./bin/check-kcov-inst`，再按
受影响范围验证补丁应用、目标内核构建及镜像启动。补丁需要对相应版本干净
源码通过 `git apply --check`，并在按顺序应用全部补丁后实际构建。

最终应交付明确的检测范围、豁免清单、工具链记录、故障注入结果、端到端
复现和开销数据。完成标准是已声明范围内的错误可检测、可定位、可复现，
而不是仅新增构建开关或成功链接 KASAN 符号。
